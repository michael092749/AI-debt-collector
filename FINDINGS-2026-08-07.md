# Findings — 2026-08-07: capacity-drop bug + 6.7s turn latency

---

## ⚠️ Part 0 — the compliance record is being written to ephemeral container disk

Found while resolving a loose end; it outranks both investigations.

`AuditStore` is the SPEC §6 compliance record. In the LiveKit Cloud deployment it is
being written to `/app/data/collector.db` **on the container filesystem**, and lost on
every restart, redeploy, or replica reschedule.

The claim rests on three premises. All three are verified.

**(1) The path resolves inside the container.** `voice_app.py:591` constructs
`AuditStore(DEFAULT_DB_PATH, ...)`. `store.py:348` resolves the bare constant through
`$COLLECTOR_DB_PATH` (`store.py:106-107`) — a fix that exists precisely for this. With
the var unset it falls back to `DEFAULT_DB_PATH = Path("data/collector.db")`
(`store.py:71`), CWD-relative, i.e. `/app/data/collector.db`.

**(2) `COLLECTOR_DB_PATH` is not set in the deployment.** Not merely absent from the
local `.env` — LiveKit Cloud injects env from deployment secrets, so the local file
proves nothing. `lk agent secrets` for `CA_4h6zwEehF26k` lists **only**:

```
ANTHROPIC_API_KEY    2026-08-07T03:20:05Z
OPENROUTER_API_KEY   2026-08-07T03:20:05Z
```

No `COLLECTOR_DB_PATH`. (Also no `COLLECTOR_VOICE_RECORDING`, independently confirming
`record=False` in production.)

**(3) LiveKit Cloud Agents offer no persistent volume.** `Dockerfile:70-83` prescribes
the remedy — *"Set `COLLECTOR_DB_PATH` to move the log off the container filesystem"* and
*"Mount the encrypted volume at /app/data with `docker run -v`, owned by UID 10001."*
That assumes a Docker host. LiveKit's docs describe agent storage as **ephemeral**
("10GB of ephemeral storage should be more than enough",
[Self-hosted deployments](https://docs.livekit.io/deploy/custom/deployments/)), document
no volume-mount facility for Cloud Agents, and point at external services instead —
secrets management explicitly cites *"API keys, database credentials"* as the intended
pattern, and log drains as the route to long-term retention. So the Dockerfile's safety
argument (0700/0600 on an encrypted mount) has no mount to stand on here.

**Corroborating observation.** Production deployed at 15:15Z; cloud calls ran at 15:25Z
(`AJ_P4gSjzDqWvZw`) and 15:36Z (`AJ_p4rJmnGDmZmL`). Neither is in the local audit DB,
which holds only 00:10–02:29Z calls from a locally-run worker:

```
cloud job AJ_p4rJmnGDmZmL present in local audit DB: False
cloud job AJ_P4gSjzDqWvZw present in local audit DB: False
```

*This is corroboration, not proof* — a file on a workstation would never receive a
container's writes regardless of durability. Premises (1)–(3) are what carry the finding.

**Two consequences:**

1. **Compliance.** Every production call's audit trail — the record SPEC §6 designates
   as authoritative, including the disclosure timeline and the agreement JSON — is
   destroyed when the replica cycles. There is currently no durable record of any call
   the deployed agent has taken.
2. **It is why this investigation needed a reproduction.** The $200 call was almost
   certainly a cloud call; its record was never missing for consent reasons — it is
   stranded on a container disk. This is a *separate* cause from `record=False`, which
   governs LiveKit Cloud upload, not local persistence.

**This needs an external durable store** — managed Postgres or equivalent, encrypted at
rest, reachable from the `us-east` agent — with its credentials injected via
`lk agent update-secrets` (the mechanism LiveKit's own docs name for "database
credentials"). That is a deployment-architecture decision plus a store-backend change,
not a config tweak: `AuditStore` is SQLite-specific today. It should be settled before
further production calls.

Note `lk agent update-secrets` **restarts the agent**, which is itself the event that
destroys the current on-disk log — so capture anything still wanted from the running
container first, if that is even reachable.

## Part 1 — "$200 works" → "$750 today, $250 next month"

### Verdict: engine-authored numbers, not model-authored

The reported call is **not in the local audit store** — all 10 calls / 78 turns were
dumped, no 750/250 pair exists. The finding below is a reproduction, not a recovered
record.

*Corrected attribution:* this is **Part 0**, not `record=False`. The 10 local calls all
predate the 15:15Z production deploy; the cloud calls' audit rows are stranded on the
container's ephemeral disk. `record=False` governs LiveKit Cloud *upload*, which is a
separate surface from local persistence.

### Reproduction (the tool ordering is a fingerprint)

| tool sequence | counter emitted |
| --- | --- |
| `propose_offer` → `record_refusal` → `concede` (engine never told the $200) | **$750 today / $250 @ 30d** |
| any path where `validate_consumer_offer(total=200)` runs first | $250 / $750 |

Only the never-told path yields $750-first.

### Where the numbers came from

`decision_engine.py:401-407`, T2 branch of `build_counter`:

```python
ceiling = total - policy.min_payment  # 1000 - 250 = 750
down = capacity if capacity is not None else ceiling  # None => take the max
amounts = (down, total - down)  # (750, 250)
```

### Where the $200 was dropped

`tools.py:537` (and the retry at `:544`) — `_concede` calls `build_counter(...)` with
**no `capacity=` argument**. It falls through `decision_engine.py:396` to
`state.signaled_capacity`, which is `None` because the only writer of that field is
`tools.py:446` inside `_validate_consumer_offer`, which never ran.
`_propose_offer` at `tools.py:481` carries the identical omission.

### Why no guardrail fired

The engine authored the numbers, so it authorized them: `_concede` records the offer
into `offers_made` (`tools.py:551`), and the numeric guard derives its authorized set
from exactly that (`guardrails/numeric.py:222-279`, via `agent.py:861-864`). $750 and
$250 are legitimately sayable, so `UNAUTHORIZED_AMOUNT` structurally cannot fire. The
codebase already names this shape at `decision_engine.py:127-131`:
*"No guardrail above the engine can catch an illegal number the engine itself authorized."*

No rule anywhere checks a plan against an accepted affordability — the guards check
numeric **provenance** only.

The model's "that works" is the trigger and violates its own system prompt
(`llm/base.py:216-218`), but nothing enforces that instruction.

### Corroboration in the DB

Call `AJ_mkJJ8crepAyW` turn 4 — consumer: *"I can make a payment of two hundred
dollars."* Recorded decision has `"signaled_capacity": null` and a counter built purely
from the $1,000 balance. `AJ_eC6f5ggvH4CD` turn 3 is the same pattern with $100.

### Why no test caught it

`tests/test_decision_engine.py:451-458`
(`test_counter_maximizes_the_downpayment_when_no_capacity_signalled`) **asserts
`installments[0] == 750.00` and `[1] == 250.00`, and passes.** It calls `build_counter`
directly with `capacity=None` passed explicitly, so it reads as a deliberate "consumer
said nothing" fixture. `tests/test_negotiation.py:160,164,169,180,189` hand-wire
`capacity=s.signaled_capacity` — the tests do exactly the plumbing `_concede` skips, so
the unit is only tested at a seam the production caller never uses.
Root cause of the blessing: `SPEC.md:86` defines `clamp(c, 250, 750)` and is silent on
`c = None`.

### Recommended fix

**Not** `capacity=context.state.signaled_capacity` at `tools.py:481/537/544` — that is a
no-op given the `decision_engine.py:396` fallback.

Make `_concede`/`_propose_offer` unreachable with an unconsumed capacity signal,
enforced in the tool layer the way `_concede` already refuses without a refusal on
record (`tools.py:517-524`): return `ok:false` with a corrective message ("the consumer
named terms — call `validate_consumer_offer` first"). No spec change needed.

Add the missing invariant to `tests/test_engine_invariants.py`: a capacity present in
`NegotiationState` must never be absent from the counter the tool layer emits.

## Part 2 — 6.7s turn latency

### Measured budget (median turn, call `AJ_p4rJmnGDmZmL`)

| Stage | Measured | Source |
| --- | --- | --- |
| EOU / endpointing → turn commit | **304 ms** (2,450 ms on 3/5 turns of the earlier call) | `user_transcript` → `llm_respond` gap |
| **LLM — 2–3 sequential blocking calls** | **6,624 ms** | `turn_latency.turn_ms` |
| — per call | **3,074 ms median** (n=19, 1,932–4,574) | `llm_respond.elapsed_ms` |
| — guardrail regeneration (extra full call) | **+3,200 ms median**, on **3 of 8 turns** | `outbound_blocked`, `label=regeneration` |
| TTS first byte (Cartesia sonic-3) | **129 ms median** (n=12, 110–209) | `turn_latency.tts_ttfb_ms` |
| **Total e2e** | **6,043 / 7,057 ms** | `turn_latency.e2e_ms` |

304 + 6,624 + 129 = 7,057 — the terms are strictly serial. The earlier call
(`AJ_P4gSjzDqWvZw`) ran 9,101–10,709 ms, so 6.7s is the good end of the range.
LiveKit's reference budget is 400–800 ms total streaming.

**The LLM stage is 93% of the latency.** STT and TTS combined are ~430 ms.

### Why each call costs 3.07s

1. **`respond()` is non-streaming** — `anthropic_client.py:195` uses `messages.create`,
   so `elapsed_ms` is full-completion time, not TTFT. A `stream()` method exists at
   `anthropic_client.py:227` and the voice path never calls it.
2. **No prompt caching anywhere.** `cache_control` is never set — only read back from
   usage (`anthropic_client.py:300-314`). A ~2,050-token static prefix (system 1,164 +
   tool schemas 886) plus the growing conversation is reprocessed uncached on every one
   of 2–3 calls per turn. Sonnet 5's 1,024-token cacheable minimum is already met.
3. **Adaptive thinking on every call** — `anthropic_client.py:205`, `:245`,
   `EFFORT = "low"` at `:59`. Thinking tokens generate before any output text.

### Structural finding

`voice_app.py:350` calls `self._negotiation_agent.turn` — the **text path**.
`agent.py:361` `stream_turn()` is fully implemented, guards sentence-by-sentence, and
its docstring says *"That is the entire sub-500ms first-audio budget."* It has **zero
production callers** (tests only). So `llm_node` emits one `yield turn.spoken` at
`voice_app.py:367-368` after everything completes, fully serializing TTS behind the last
LLM call.

> ⚠️ **Why caching was demoted from #1 to #5.** The original 1,200–3,300 ms figure
> assumed cache hits reduce the measured 3,074 ms. But `respond()` is non-streaming, so
> that number is **full-completion** time, not TTFT. Caching reduces input processing and
> TTFT — it does **not** reduce output-token or thinking-token generation. The
> discriminating check (per-call `input_tokens` vs `output_tokens`, read back at
> `anthropic_client.py:300-314`) **cannot be run today** — see "Loose ends" below. The
> proxy evidence there points at thinking-token generation, not prefill, as the dominant
> term, which is what moved thinking to #2.

**Corrected totals.** #1 is the only **measured** line; treat everything below it as
provisional. #1 + #3 takes a 6.7s turn to ~3.5–4.5s on turn 1 and ~4.5–5.5s afterward.
Reaching ~3.35s reliably needs #2 or #4 as well.

**Not recommended:** re-enabling `preemptive_generation` (`voice_app.py:161`). The
comment there is correct — `turn()` has side effects (advances `_turn_index`, records a
`ConsumerUtterance`, moves the concession ladder) in a non-cancellable thread, so a
discarded preflight generation corrupts the audit trail.

### Cleared with evidence

- **Region/placement is fine.** Agent in US East B, LiveKit Inference in-cluster
  (`inference.livekit.svc.cluster.local`), TTS TTFB 110–209 ms. No cross-region penalty.
- **STT/TTS are not the bottleneck** — ~430 ms of a 6,700 ms turn.

### Loose ends — both now resolved

**Recording flag: no bug, no compliance violation.** `voice_app.py:651` passes
`record=_recording_options()`. That function returns `False` because
`COLLECTOR_VOICE_RECORDING` is unset (confirmed absent from `.env`). The
`"enable_recording": true` in the job request is the **project-level** LiveKit Cloud
observability setting — necessary but not sufficient; the session-level `record=False`
wins. Deployed behavior matches the R2 consent posture exactly.

This is also the direct cause of *"No observability data available"* in the Agent
insights tab. The intended remedy is already implemented and unused:
`COLLECTOR_VOICE_RECORDING=diagnostics` → `{"audio": False, "transcript": False,
"traces": True, "logs": True}`. Traces and logs, **no audio and no transcript** — the
Agent-insights timeline without a third-party copy of the consumer's speech. Per the
docstring at `voice_app.py:227-245`, still a deliberate per-deployment decision.

**Token accounting: not obtainable from any current source — the caching estimate stays
unvalidated, and the ranking moved because of it.** The one measured proxy:
`tts_usage.characters_count` = 1,119 chars over 6 spoken turns and 621 over 4 → roughly
**40–47 tokens of visible spoken output per turn**, against a ~2,050-token static input
prefix. Prefill on 2–3k tokens is order 100–300 ms, so caching plausibly saves
**200–750 ms/turn, not 1,200–3,300** — about 5× less than first estimated. The sharper
consequence: if input processing is only ~200 ms and visible output only ~45 tokens,
then most of the 3,074 ms per call is **token generation, and mostly adaptive-thinking
tokens**. That is why thinking is now #2 and caching #5.

Why the real numbers are unreachable:
`ModelCalled` is the only carrier of tokens/cost/`cache_read_tokens`
(`audit/events.py:187-196`, emitted at `agent.py:788`), and `llm_respond` logs only
`turn`/`label`/`elapsed_ms` (`agent.py:767-774`) — no tokens. The audit DB contains
**zero `model_call` rows**: `turns.event_type` holds only `turn` (52) and
`guardrail_trip` (26), despite `EventType.MODEL_CALL = "model_call"`
(`audit/events.py:53`). `_record()` (`agent.py:1110-1120`) routes `ModelCalled` to
`self.trace` (inert — no exporter under `record=off`) and to `self.store`, which in
production is the ephemeral container SQLite described in **Part 0**. Not in the drain,
not retrievable from a finished job. Consequence: **cost and cache effectiveness are
unmeasurable in production today.** Fix #6 is the ~3-line unblock.

**Tail risk (unchanged):** `TIMEOUT_SECONDS = 6.0` with `MAX_RETRIES = 1`
(`anthropic_client.py:65-66`) means one stalled call can burn 12s wall-clock. No retry
fired in this sample (max observed 4,574 ms), but the constant's own comment claims a
~1.5s tolerance it does not enforce.

## The link between the two parts

**Not the same event** — different calls. Part 1's `MINI_MIRANDA_NOT_FIRED` is turn 4 of
`AJ_mkJJ8crepAyW`; Part 2's regeneration measurements are turn 1 of `AJ_p4rJmnGDmZmL`
and `AJ_P4gSjzDqWvZw`. The defensible claim is narrower: the Mini-Miranda guard trips
frequently **across** calls, costs a full regeneration round-trip each time, and appears
on the same turns where capacity gets dropped. So fix #2 pays off twice.

**The load-bearing link is different, and it constrains the fix order:** the *blocked*
text on `AJ_mkJJ8crepAyW` turn 4 already contained the $1,000 / 4×$250 counter. The
regeneration rewrites **prose, not numbers** — the engine bug survives regeneration
intact. Fix #2 therefore does nothing for Part 1, and Part 1's fix does nothing for
latency. They are independent defects that happen to co-occur on the same turns.
